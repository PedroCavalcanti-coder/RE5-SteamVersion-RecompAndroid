# Revisión del proyecto y siguiente etapa

Fecha: 2026-10-07. Revisión estática de fuentes propias, configuración,
pipeline, runtime de pcrecomp, documentación y registros existentes; inspección
dirigida del catálogo y desensamblado del binario de análisis. No se ejecutó
una nueva sesión del juego ni una nueva compilación. Los resultados de ejecución
citados pertenecen a las sesiones guardadas del 2026-10-06.

## Estado real

- El proyecto principal es `nfsu2-recompiled`; `pcrecomp` proporciona el lifter
  y el runtime. `reference/nfsu2-re` aporta nombres y referencias de ingeniería
  inversa. `scratch/pc_test` es otro checkout, no el runtime seleccionado por CMake.
- El SHA-256 de la instalación coincide con el documentado:
  `f9dd86c054878ce6276beb07c1fd61874f7a1e4bf1f241b084c65b73e24168a7`.
- Hay C generado, catálogo de funciones, ejecutable y símbolos de depuración.
  Los registros muestran arranque, recursos de shaders, D3D9 y Present correctos.
  La visualización de las intros está documentada como observación del usuario.
- Menú navegable, garaje y carrera aún no están verificados.
- La salida es recompilación estática a C con registros y memoria de x86
  simulados; no es una reconstrucción del código fuente original de alto nivel.
- El host actual requiere MSVC x86, Win32 y D3D9 reales. No hay proyecto NDK,
  Gradle, host ARM64 ni backend gráfico Android en este proyecto.
- Había cambios locales previos en `src/runtime/dinput_trace.c`; se conservaron.

## Entrada: lo que ya sabemos

Fuente principal: `logs/run_20261006_161815.log`.

1. DirectInput se crea y el dispositivo que recibe el mapa de acciones consigue
   Acquire. GetDeviceData entrega eventos repetidos de presionar (`0x80`) y
   soltar (`0x00`), con `uAppData=0x1F` y `0x22`. Por tanto, no es correcto
   afirmar que no llega ninguna entrada. No se identificó aún la tecla física
   de cada evento ni su recorrido completo hasta el frontend.
2. Cuatro BuildActionMap tienen formatos inicializados y devuelven éxito.
   Las tres llamadas fallidas reciben estructuras con tamaño, número de
   acciones y demás campos a cero. Esto explica el parámetro inválido observado,
   pero falta comparar con el original para saber por qué están vacías y si
   son relevantes para el problema.
3. SetActionMap devuelve `0x0000000B` (DI_SETTINGSNOTSAVED), un resultado de
   éxito documentado: por sí solo no demuestra que no se aplicó el mapa.
   Referencia: https://learn.microsoft.com/en-us/previous-versions/windows/desktop/ee417919(v=vs.85)
4. Los fallos del ratón al perder foco son compatibles con el modo exclusivo
   en primer plano. No explican por sí solos los eventos de teclado recibidos
   mientras siguen presentándose fotogramas.

### Recorrido localizado en el binario

- Callback de EnumDevicesBySemantics: `0x5CA660`, llama a `0x5C1080`.
- `0x5C1080`: construye los cuatro mapas desde `0x86F348`, los tres formatos
  adicionales vacíos, y aplica el mapa de `0x86F490`.
- `0x5C15F0`: Poll, GetDeviceData, consulta GetObjectInfo y procesa pulsaciones.
- `0x5C1840`: otra ruta de Poll/GetDeviceData; su rama de lectura depende de
  `[this+0x234] == 0x13`. Después consulta `0x870768` y actualiza máscaras en
  `[this+8]` / `[this+0xC]` según `uAppData`.
- El catálogo identifica `0x5CF220` como llamador directo de ambas rutas.

Estas direcciones son puntos de instrumentación; aún no prueban qué rama está
activa durante la intro ni dónde se pierde o ignora la acción.

### Defectos del trazador que afectan al diagnóstico

- El registro dice que DIACTIONA mide 0x34 bytes, pero el formato observado
  usa 40 bytes (0x28) en x86. Lee `dwHow` mediante `act[12]`; corresponde a
  `act[9]`. El valor impreso sale fuera de la acción actual.
- La detección de dispositivos por comparación con la vtable del ratón
  confunde AddRef compartidos: el log registra como `dev1` el mismo puntero
  del objeto IDirectInput8. También puede omitir métodos de otra vtable.
- Sólo muestra el primer evento de cada lote, limita el total a 64 registros
  y sólo registra eventos si HRESULT es exactamente cero. Falta registrar
  resultados no negativos con eventos, incluido desbordamiento del buffer,
  el tamaño efectivo del elemento y el llamador guest.

## Riesgos del runtime y portabilidad

- `native32.c` guarda por hilo registros enteros, x87 y MMX, pero `regs_t`
  no incluye XMM, MXCSR ni los flags globales publicados. El proyecto añade
  XMM/MXCSR como globales. Revisar su conservación en cambios de hilo y
  callbacks; es una carencia verificable del estado guardado, no una causa
  demostrada del problema de teclado.
- El puente y los callbacks de native32 dependen de ensamblador MSVC x86 y
  excepciones de Windows. Deben sustituirse para ARM64.
- No basta con compilar el C generado para 64 bits: guest pointers de 32 bits
  no pueden almacenar punteros arbitrarios del host. Hace falta definir memoria
  guest, asignadores, handles y traducción de buffers/callbacks/vtables.
- `win32hle` ya existe en pcrecomp como base portable, pero sus pruebas descritas
  son de huéspedes sintéticos de 32 bits y su asignación/paso de punteros
  conserva conversiones directas a uint32_t. No es un host ARM64 de NFSU2 listo.
- La cobertura del lifter y los tests documentados ayudan, pero no certifican
  toda la semántica ni los subsistemas que aún no se han ejecutado.
- El inventario D3D9 sólo cubre el arranque y la intro. Una carrera ampliará
  métodos, shaders, estados y formatos necesarios.
- Las excepciones C++/SEH guest siguen siendo un riesgo documentado pendiente.

## Orden recomendado para continuar

1. **Medición fiable del teclado en Windows.** Corregir el trazador; registrar
   identidad real del dispositivo, mapa completo y todos los eventos del lote
   con llamador guest. Instrumentar las rutas localizadas, flags de contexto,
   máscaras y entrega de acciones al frontend. Comparar una secuencia conocida
   de Enter, Escape y flechas con el ejecutable original en la misma instalación.
   Evitar asumir que las tres estructuras vacías son la causa.
2. **Cerrar una prueba jugable de PC.** Saltar/terminar intros, entrar al menú,
   navegar, abrir garaje y ejecutar una carrera con dirección, aceleración y
   freno. Verificar carga de archivos, sonido, guardado y recuperación de foco.
   Capturar el inventario gráfico de esa sesión.
3. **Separar el host del juego.** Mantener Windows como referencia y definir
   APIs de memoria guest, handles, callbacks, hilos, archivos, tiempo, entrada,
   audio y gráficos. Primero conservar serialización del guest hasta tener
   estado completo por hilo y pruebas de sincronización; quitar el lock global
   es una optimización posterior, no un requisito para iniciar Android.
4. **Probar ARM64 por capas.** Host mínimo y pruebas de memoria/punteros,
   dispatch y callbacks antes de intentar el juego completo. Inventariar los
   imports usados contra la cobertura real de HLE. Incorporar luego ventana y
   ciclo de vida Android, entrada mediante acciones, audio y traducción D3D9.
5. **APK de demostración.** Arranque reproducible, datos de la instalación del
   usuario, menú, controles táctiles/mando y una carrera. Medir rendimiento y
   memoria en hardware real antes de optimizar.

## Documentación pendiente

README aún dice que M6 está bloqueado por el disco, mientras STATUS ya marca
M6–M9 completos. Los siguientes pasos de STATUS siguen proponiendo resolver
el disco y recursos, aunque el código y registros muestran esas etapas superadas.
La próxima actualización debe reflejar que llegan eventos de entrada y que falta
seguir su consumo, distinguiendo resultados históricos de nuevas verificaciones.

Resultado de esta revisión: hay una base real de recompilación Windows que ya
renderiza; el siguiente hito concreto es entrada funcional hasta una carrera.
Android requiere una segunda implementación del host, además del C generado.
